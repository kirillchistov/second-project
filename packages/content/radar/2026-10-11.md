# Радар изменений: 2026-07-13 — 2026-10-11

## Значимые изменения

- **React и React DOM 19.3.0** — Компонент <ViewTransition> и функция addTransitionType стали стабильными. Анимации enter/exit/update/share запускаются только для обновлений внутри Transition: startTransition, раскрытие <Suspense>, useDeferredValue. Обёртка <ViewTransition> вокруг Suspense анимирует переход от fallback к контенту и заставляет картинки и шрифты внутри неё приостанавливаться до загрузки. ([источник](https://react.dev/blog/2026/09/09/react-19-3))
- **React и React DOM 19.3.0** — Стабилизированы Fragment Refs: <Fragment ref={...}> отдаёт FragmentInstance. Через него можно работать с DOM-детьми фрагмента как с группой: addEventListener/removeEventListener/dispatchEvent, focus/focusLast/blur, observeUsing для IntersectionObserver и ResizeObserver, getClientRects, scrollIntoView. Для этого не нужен лишний div-обёртка и не нужно, чтобы дочерний компонент пробрасывал ref. ([источник](https://react.dev/blog/2026/09/09/react-19-3))
- **React и React DOM 19.3.0** — <Context> теперь можно рендерить прямо в Server Components. В React DOM добавлена поддержка Trusted Types. ([источник](https://react.dev/blog/2026/09/09/react-19-3))
- **Next.js (App Router) 16.4** — Cache Components ('use cache', cacheLife) вместе с Partial Prefetching (флаги cacheComponents и partialPrefetching) рекомендованы для всех приложений. В create-next-app эта модель включена по умолчанию, а в Next.js 17 станет поведением по умолчанию. Она заменяет неявное кэширование прежних версий App Router. ([источник](https://nextjs.org/blog/next-16-4))
- **Next.js (App Router) 16.4** — Новая опция сегмента export const ensureStatic = 'navigation' | 'prefetch' | 'shell'. Она валит сборку, если в маршрут или layout попадает динамический контент, и так гарантирует статичность shell, prefetch или всей навигации. ([источник](https://nextjs.org/blog/next-16-4))
- **Next.js (App Router) 16.4** — Новые API navigation() и prefetch() из next/cache. await navigation() исключает кэшированный контент из prefetch и откладывает его до реального перехода. await prefetch() исключает контент из shell маршрута до явного prefetch. ([источник](https://nextjs.org/blog/next-16-4))
- **Next.js (App Router) 16.4** — Добавлена команда next upgrade --agent, которая готовит агенту миграционные гайды, codemods и шаги проверки. Опция experimental.agentUpgrade ('security' по умолчанию, 'latest' или false) напоминает о доступных обновлениях во время next dev и next build. ([источник](https://nextjs.org/blog/next-16-4))

## Затронутые вопросы

### Что такое фрагменты и зачем они нужны? (`fragments`)

В React 19.3 Fragment принимает не только key, но и ref. Ref даёт FragmentInstance для работы с DOM-детьми группой: события, фокус, наблюдатели, измерения. Тезис «если нужно навесить ref или слушатель на группу узлов, придётся добавить обёртку» больше не верен. Упражнения про назначение фрагментов стоит дополнить сценарием с ref.

**Правка вопроса:** В краткий ответ дописать: «С React 19.3 полной форме <Fragment> можно передать ref — он даёт FragmentInstance (addEventListener, focus, observeUsing, getClientRects, scrollIntoView и др.), что позволяет работать с DOM-детьми без обёртки-div».

### Что такое React Server Components? (`server-components`)

С React 19.3 <Context> можно рендерить прямо в Server Components. Стандартный ответ «провайдер контекста обязательно выносится в отдельный клиентский компонент с 'use client'» нужно уточнить. Объяснение границы server/client и работы контекста стоит дополнить этим изменением.

**Правка вопроса:** В краткий ответ дописать: «С React 19.3 <Context> можно рендерить непосредственно в Server Components».

### Что изменилось в React 19 для повседневного кода? (`react-19-changes`)

В минорном релизе 19.3 стабилизированы <ViewTransition> с addTransitionType и Fragment Refs, появились <Context> в Server Components и поддержка Trusted Types. Обзор изменений React 19 следует дополнить этими пунктами, чтобы кандидат знал, что относится к 19.0, а что к 19.3.

**Правка вопроса:** В краткий ответ дописать: «В React 19.3 стабилизированы <ViewTransition>/addTransitionType и refs у <Fragment>, а <Context> можно рендерить в Server Components».

### Чем отличаются CSR, SSR, SSG и ISR? (`rendering-strategies`)

В Next.js 16.4 модель Cache Components рекомендована для всех приложений и включена по умолчанию в create-next-app. Статический и динамический контент теперь смешиваются в одном ответе через 'use cache' и cacheLife, а не выбираются стратегией на уровне всей страницы. Деление CSR/SSR/SSG/ISR стоит дополнить этой моделью и опцией ensureStatic для гарантии статичности.

**Правка вопроса:** В краткий ответ дописать: «В Next.js 16.4+ по умолчанию используется модель Cache Components: статические ('use cache') и динамические части страницы рендерятся и стримятся в одном ответе, а ensureStatic позволяет гарантировать полностью статичный маршрут».

## What are Cache Components?
Cache Components are a suite of features that lets you mark specific parts of your component tree as eligible for caching. Think of `'use cache'` as a component-level version of the Cache-Control HTTP header:

import { cacheLife } from 'next/cache';

## What's new in Cache Components
In this post, we use "Cache Components" to refer to the new programming model, which you can use today by enabling two flags in your Next.js config:

import type { NextConfig } from 'next';

### Ensuring shells, prefetches, or pages are static
One of the hallmark features of `'use cache'` is the ability to build pages that stream static and dynamic content together in a single response from the server.
For example, you can compose the current user’s avatar alongside a blog post that is otherwise statically prerendered:
```jsx
export default function Page() {
return (
<>
);
}
// This component renders at request time
async function UserAvatar() {
const currentUser = await getCurrentUser();
// ...
}
// This component is statically prerendered
async function Content() {
'use cache';
await fetch('...');
// ...
}
```
Next.js can serve the prerendered blog post from cache (like your app's `/public` folder, or a CDN) and render the UserAvatar at request time, all from the same HTTP response.
This flexibility is what enables you to build apps with sophisticated UIs, without sacrificing speed or dynamism. But sometimes you _want_ to build an app with fully static pages. In those cases, one dynamic component can degrade the performance or cost characteristics of an otherwise optimized site.
In Next.js 16.4, `ensureStatic` offers a simple way to guarantee that a route’s shell, prefetch, or full navigation is static. For apps that want to avoid unintentional compute and keep their server costs down, this lets you prevent a dynamic component from accidentally sneaking into a route.
For example, if we wanted to enforce that our blog post page from the example above was always static, and that adding a dynamic component like UserAvatar should never be possible, we could add `export const ensureStatic` to the route:
```jsx {1,6}
export const ensureStatic = 'navigation';
export default function Page() {
return (
<>
{/* 🔴 This component fails the build */}
);
}
```
By setting `ensureStatic` to "navigation", Next.js will fail the build if any dynamic content is ever included in this page, ensuring that navigations to this route will never render at request time.
While "navigation" is the most restrictive form, you can also set `ensureStatic` to "prefetch" (to ensure links with explicit prefetching to this route only fetch static content) or "shell" (to ensure that only static content is fetched when this route is first discovered) if you need more fine-grained control.
In addition to using it on individual pages, you can also add `ensureStatic` to a layout to apply the same guarantees to all pages within that layout. For example, you could add `ensureStatic = 'navigation'` to the root layout to easily guarantee that every page navigation in your site is static:
```jsx {2}
// app/layout.tsx
export const ensureStatic = 'navigation';
export default async function RootLayout({ children }) {
// ...
}
```
Then, you could push it down to nested layouts if certain pages start to need dynamic content.
Many dynamic apps won't need this feature, but for optimized sites like ecommerce stores, marketing pages, or blogs, `ensureStatic` is a simple way to guard against unwanted request-time rendering.
Learn more about [keeping pages static](/docs/app/guides/keeping-pages-static) and the [`ensureStatic` config](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic).
### Excluding content from a prefetch
Prefetching is a powerful way to improve the UX of your Next.js applications.
By using ` ` or `useRouter().prefetch()`, you can eliminate loading states by prerendering a page's cached UI before an actual navigation takes place.
For example, let's look at a simple email app. Here's an Inbox that renders links to each message:
{/* prettier-ignore */}
```jsx {7-12}
async function Inbox() {
const messages = await db.query.messages.findMany();
return (
);
}
```
And here's the Message page, which shows a spinner when loading a message thread for the first time, then caches it in the browser for subsequent visits:
{/* prettier-ignore */}
```jsx {4,31,37}

return (
}>
{params.then(({ id }) => (
))}
);
}
async function Message({ id }) {
const [message, thread] = await Promise.all([
getMessage(id),
getThread(id)
]);
return (
<>
{message.subject}
{message.body}
{thread.map((message) => (
{message.body}
))}
);
}
async function getMessage(id) {
'use cache';
return db.query.messages.findFirst({ where: eq(messages.id, id) });
}
async function getThread(id) {
'use cache';
return db.query.messages.findMany({
where: eq(messages.threadId, id),
orderBy: asc(messages.createdAt),
});
}
```
While this lets users instantly view messages they've already loaded, they'll still see the loading spinner when opening a message for the first time.
To eliminate that initial loading state, we could add `prefetch` to our Inbox's links:
{/* prettier-ignore */}
```jsx {8}
async function Inbox() {
const messages = await db.query.messages.findMany();
return (
);
}
```
Now, each link will prefetch all the cached data and UI on the Message page as soon as it becomes visible, so it's ready by the time the user clicks.
This makes for a great UX by eliminating loading states from the app, but it also means that every visible link loads the _entire_ message thread ahead of time—even for messages the user never opens. For our email app, this might be too costly or introduce too much strain on our servers.
Instead of just turning prefetching back off, a better solution would be to only prefetch the first message, and defer rendering the rest of the thread until the user actually navigates.
In Next.js 16.4, we can do exactly this. The new `navigation` API lets you exclude loading cached content during a prefetch, effectively deferring it until an actual navigation takes place.
In our example, we could extract the thread into a new component, and add `await navigation()` to exclude it from the prefetch:
```jsx {1,19}
import { navigation } from 'next/cache';
async function Message({ id }) {
const message = await getMessage(id);
return (
<>
{message.subject}
{message.body}
}>
);
}
async function Thread({ id }) {
await navigation();
const thread = await getThread(id);
return (
<>
{thread.map((message) => (
{message.body}
))}
);
}
```
Now the Message page only renders the first message during a prefetch, and waits for a full navigation to load the rest of the thread from the database and render it.
In addition to `navigation()`, we've also added `prefetch()`, which you can await to exclude cached content that would otherwise be included in a route's shell. This way, rendering that content will be deferred until an explicit prefetch with ` ` or `useRouter().prefetch()`.
These APIs give you more control over what data gets loaded at different stages of a navigation, letting you balance eager and lazy rendering in a way that’s right for your app.
Learn more about [deferring work to a later stage](/docs/app/guides/optimizing-prefetching#defer-work-to-a-later-stage), and see the [`navigation`](/docs/app/api-reference/functions/navigation) and [`prefetch`](/docs/app/api-reference/functions/prefetch) API references.

New React Features
View Transitions
The new <ViewTransition> component lets you animate elements as they enter, exit, move, or resize using the browser’s View Transition API . We shared it as an experimental API last year , and in 19.3 it’s stable and ready to use.
To animate part of your UI, wrap it in <ViewTransition> :
import { ViewTransition } from 'react' ;
{ isShowing && (
< ViewTransition >
< Component />
</ ViewTransition >
) }
Now, whenever an update marked as a Transition changes the child component’s style, or causes the ViewTransition to be mounted or unmounted, React will animate that update.
React chooses which animation to run based on how the tree changed:
enter : the <ViewTransition> is added.
exit : the <ViewTransition> is removed.
update : the children of a <ViewTransition> change style or content.
share : a named <ViewTransition> is removed in one place and added in another.
Note that updates not marked as Transitions don’t trigger animations, as those are meant to be urgent and reflected immediately in the UI. State updates inside of startTransition , a <Suspense> reveal, or an update from useDeferredValue all cause a View Transition to animate.
Here’s a simple example of an enter/exit animation:

import videos from './data' ;

By default, <ViewTransition> animates with a smooth cross-fade. You can customize each kind of animation by passing a View Transition Class and defining the animation in CSS, or you can use the Web Animations API to trigger animations imperatively with the event props ( onEnter , onExit , onShare , onUpdate ).
Currently, <ViewTransition> only works in the DOM. We’re working on support for React Native and other platforms.
For more, see the <ViewTransition> docs .
addTransitionType
Sometimes, you’ll want to customize which animation is used for the same state update. For example, navigating a carousel forward to the third slide should animate the slides right-to-left, while navigating it backward should animate them left-to-right, even though both actions set the currentSlide to 3.
You can customize the animation for a given View Transition by calling addTransitionType alongside the state update. This lets you add more information about the cause of a particular transition:
function nextSlide ( ) {
startTransition ( ( ) => {
addTransitionType ( 'next' ) ;
setCurrentSlide ( c => c + 1 ) ;
} ) ;
}
function previousSlide ( ) {
startTransition ( ( ) => {
addTransitionType ( 'previous' ) ;
setCurrentSlide ( c => c - 1 ) ;
} ) ;
}

'previous' : 'from-left' ,

'next' : 'to-left' ,
'previous' : 'to-right' ,
} }
>

</ ViewTransition >

Animating fallbacks, images, and fonts with Suspense
One of the most exciting things about View Transitions in React is how they integrate with Suspense.
You can animate a Suspense boundary as it reveals its children by wrapping it in <ViewTransition> :
< ViewTransition >
< Suspense fallback = { < Loading /> } >
< Component />
</ Suspense >
</ ViewTransition >
When the children finish loading, React will trigger an update animation from the fallback to the final content.
Here’s an example. Try pressing ➕ to render a LazyVideo that suspends the first time it’s rendered:

While this works, you’ll notice that the video also animates in and out on subsequent reveals, even though it’s already been loaded. (You might also notice that the fallback fades in the first time it’s shown.)
In general, animations with Suspense work best when they’re used sparingly, and avoided for cached UI that would otherwise appear instantly.
Here are some principles for achieving good UX when animating with Suspense:
Fallbacks should appear immediately without animation
A fallback should update to its final content with animation
Children that don’t suspend should appear immediately without animation
This keeps your app feeling snappy when things are already loaded, and only uses animation to make the update from fallback to final content more seamless.
To fix our example above, we can disable all animations other than updates:
< ViewTransition update = "auto" default = "none" >
< Suspense fallback = { < Fallback /> } >
< Component />
</ Suspense >
</ ViewTransition >

Fragment Refs
When you need lower-level control over a component’s DOM nodes—for example to attach an event listener, observe visibility, or move focus—you can usually use a ref. But there are some situations where this is difficult:
Components that render a group of siblings with no single parent
Components that don’t pass along their ref prop to another element
function Component ( ) {
// How can we work with the list of DOM nodes rendered by this component?
return (
{ posts . map ( post => (
< Heading key = { post . id } >
{ post . title }
</ Heading >
) ) }
)
}
Adding a wrapper <div> just to hold a ref sometimes works, but it can also interfere with your component’s styling or layout. Moreover, if a component doesn’t expose a ref prop, you would need to modify that component to do so, which might be impossible if it comes from a library you don’t control.
Fragment Refs solve these problems by providing a limited set of commonly used DOM methods that work with any React component, regardless of what it renders.
In 19.3, you can use them by passing a ref directly to a <Fragment> . This ref gives you a FragmentInstance , which you can use to work with the Fragment’s DOM children:
function Component ( ) {
const fragmentRef = useRef ( null ) ;
useEffect ( ( ) => {
const fragmentInstance = fragmentRef . current ;
fragmentInstance . focus ( ) ;
} , [ ] ) ;
return (
< Fragment ref = { fragmentRef } >
{ posts . map ( post => (
< Heading key = { post . id } >
{ post . title }
</ Heading >
) ) }
</ Fragment >
)
}
The FragmentInstance operates on the children’s DOM as a group , without changing its structure:
addEventListener , removeEventListener , and dispatchEvent manage events for first-level children.
focus , focusLast , and blur move focus across nested children, depth-first.
observeUsing and unobserveUsing connect an IntersectionObserver or ResizeObserver .
getClientRects , getRootNode , compareDocumentPosition , and scrollIntoView let you measure and scroll to the fragment’s first-level children.
Thus, Fragment Refs let you attach behavior to other components without requiring you to modify those component’s internals, or without changing the DOM structure that they already produce.
