# Как отменить fetch-запрос с помощью AbortController?
@slug abort-controller
@topic fullstack
@verified react@19.3
@updated 2026-11

> `AbortController` создаёт `signal`, который передаётся в `fetch`. Вызов `controller.abort()` обрывает запрос, а `fetch` реджектится с `AbortError`. Так отменяют устаревшие запросы — например, если пользователь уже перешёл на другую страницу.

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setUser)
    .catch((err) => {
      if (err.name !== 'AbortError') setError(err);
    });
  return () => controller.abort();
}, [id]);
```

Без отмены запрос всё равно долетит до сервера, а ответ, если он ещё докачивается, продолжит идти впустую — отмена обрывает соединение и экономит трафик на недополученной части. Но сервер не получает команды «откати операцию»: если он уже начал обрабатывать запрос (например, пишет в базу), эта работа обычно доводится до конца — отмена не откатывает побочные эффекты на сервере. А вот если промис `fetch` уже успел выполниться до вызова `abort()` (ответ пришёл, `.then` встал в очередь), отмена задним числом его не остановит — здесь нужна ручная проверка `signal.aborted` перед `setUser`, а не расчёт на `AbortError`.

Один `AbortController` можно использовать для нескольких `fetch` сразу: `abort()` отменит их все одним вызовом. Это удобно, когда страница параллельно грузит несколько ресурсов и уходит с нее до того, как все они успели прийти. Но после одного `abort()` `signal` навсегда остаётся в состоянии aborted — для следующего запуска эффекта нужен новый `AbortController`, который и создают внутри эффекта.

### Подводные камни
- Забыть `catch` для `AbortError` — пользователь увидит ложную ошибку вместо тихой отмены.
- Завести один `controller` на весь компонент (вне эффекта): после первого `abort()` его `signal` необратимо aborted, и каждый следующий `fetch` с тем же сигналом отменяется мгновенно.
- Думать, что `abort()` останавливает запрос на сервере — он просто перестаёт слушать ответ.

# Когда fetch-запрос реджектится, а когда нет?
@slug fetch-error-handling
@topic fullstack

> `fetch` реджектится только при сетевой ошибке: нет соединения, DNS не резолвится, CORS заблокировал ответ. Ответ со статусом 404 или 500 — это **выполненный** промис с `response.ok === false`. Проверять `response.ok` нужно отдельно, иначе ошибки сервера пройдут незамеченными.

```tsx
const res = await fetch('/api/todos');
if (!res.ok) {
  throw new Error(`Сервер ответил ${res.status}`);
}
const data = await res.json();
```

Частая ошибка новичков — обернуть `fetch` в `try/catch` и решить, что `catch` поймает и 404, и 500. Не поймает: промис выполнился, просто с «плохим» телом. Если не проверить `response.ok`, компонент попытается распарсить JSON ошибки как успешные данные или получит `undefined` там, где ждал массив.

Отдельно стоит проверка `Content-Type` ответа: если сервер в случае ошибки вернул HTML-страницу (например, 502 от прокси), `response.json()` упадёт с ошибкой парсинга — это тоже стоит обрабатывать отдельно от бизнес-ошибок.

### Подводные камни
- Проверять только `catch`, не проверяя `response.ok` — HTTP-ошибки проходят как успех.
- Вызывать `response.json()` до проверки статуса, когда тело может быть не JSON.

# Чем axios отличается от fetch и когда нужна библиотека поверх него?
@slug fetch-vs-axios
@topic fullstack

> `fetch` — встроенный низкоуровневый API: без интерсепторов, без автопарсинга JSON, без отмены по таймауту «из коробки» и с нетипичным поведением ошибок (см. вопрос про `response.ok`). `axios` добавляет поверх HTTP-клиента интерсепторы, автоматический JSON, прогресс загрузки и реджект промиса на ошибочном статусе.

Для простого приложения с парой запросов `fetch` достаточно — не нужно тянуть зависимость ради того, что легко написать в десяток строк обёрткой. Библиотека оправдана, когда нужны сквозные интерсепторы (например, подстановка токена и обработка 401 в одном месте для всех запросов), отмена запросов по токену отмены старого образца, или поддержка окружений без `fetch` (очень старые среды, что сегодня редкость).

На практике многие команды пишут тонкую обёртку над `fetch` (проверка `response.ok`, типизация, базовый URL) и этого хватает; другие берут `ky` или `axios` ради готовых интерсепторов. RTK Query и TanStack Query используют `fetch` под капотом по умолчанию — выбор клиента почти не важен, если кэширование и инвалидация решены на уровне этих библиотек.

### Подводные камни
- Тащить `axios` только ради автопарсинга JSON — это одна строка с `fetch`.
- Не знать, что `axios` по умолчанию реджектит промис на 4xx/5xx — переносить это предположение на `fetch` и ловить ошибки не там.

# Как отправить файл или форму через fetch?
@slug fetch-formdata
@topic fullstack

> Для файлов и смешанных полей тело запроса собирают через `FormData`, а не `JSON.stringify`. Браузер сам выставит `Content-Type: multipart/form-data` с нужным boundary — вручную его указывать нельзя, иначе граница между полями потеряется.

```tsx
const formData = new FormData();
formData.append('avatar', fileInput.files[0]);
formData.append('name', 'Ира');

await fetch('/api/profile', { method: 'POST', body: formData });
```

`FormData` можно собрать и прямо из DOM-формы: `new FormData(formElement)` берёт все поля с атрибутом `name`. Для JSON-полей внутри multipart-запроса их сериализуют в строку: `formData.append('meta', JSON.stringify({ tags: ['a'] }))`.

Прогресс загрузки через `fetch` отследить нельзя — для этого нужен `XMLHttpRequest` с событием `progress` или библиотека, построенная поверх него. Это одна из причин, по которой для экранов загрузки файлов с прогресс-баром иногда возвращаются к `XMLHttpRequest` или берут `axios`.

### Подводные камни
- Вручную ставить заголовок `Content-Type: multipart/form-data` — без boundary сервер не распарсит тело.
- Пытаться отследить прогресс загрузки через `fetch` — API для этого не даёт событий.

# Что такое WebSocket и чем он отличается от обычных запросов?
@slug websocket-basics
@topic state

> HTTP-запрос — это пара «запрос → ответ», после которой соединение обычно закрывается. WebSocket начинается как HTTP-запрос с заголовком `Upgrade: websocket`, но после рукопожатия соединение остаётся открытым, и обе стороны — и клиент, и сервер — могут слать сообщения в любой момент, без нового запроса на каждое.

```tsx
const ws = new WebSocket('wss://example.com/chat');
ws.onopen = () => ws.send(JSON.stringify({ type: 'join' }));
ws.onmessage = (event) => console.log(JSON.parse(event.data));
ws.onclose = () => console.log('соединение закрыто');
ws.onerror = (err) => console.error(err);
```

WebSocket нужен там, где сервер должен сам инициировать сообщение клиенту: чат, live-обновления котировок, совместное редактирование, уведомления. Для сценария «клиент иногда опрашивает сервер» обычного `fetch` по таймеру или polling часто достаточно и проще в реализации — постоянное соединение стоит держать только когда задержка и частота событий это оправдывают.

### Подводные камни
- Держать WebSocket-соединение там, где хватило бы редкого polling — лишняя сложность на клиенте и сервере.
- Забывать закрывать соединение при размонтировании компонента — утечка открытых сокетов.

# Зачем нужен Redux, если есть useState и Context?
@slug why-redux
@topic state

> `useState` хранит состояние одного компонента, `Context` рассылает значение вниз по дереву, но ни то, ни другое не даёт предсказуемых переходов состояния, единого места для логики изменений и инструментов отладки вроде time-travel. Redux нужен, когда состояние действительно общее для многих несвязанных частей приложения и важно трассировать, кто и почему его поменял.

Context сам по себе — это просто способ передачи значения, он **не решает** задачу хранения и изменения состояния: обычно его сочетают с `useReducer`, и тогда получается маленькая ручная версия Redux без middleware и DevTools. Проблема чистого Context в том, что при смене значения перерисовываются все подписанные компоненты — без дополнительных мер селекторы здесь не работают так, как в Redux (см. вопрос про `useSyncExternalStore`).

До того как тянуть Redux, стоит честно спросить: это состояние действительно глобальное и клиентское, или это копия серверных данных (тогда нужен TanStack Query или RTK Query, а не Redux), или оно нужно лишь паре соседних компонентов (тогда достаточно поднять state к общему предку)?

### Подводные камни
- Класть в Redux серверное состояние (списки с сервера, кэш API) вместо клиентского UI-состояния — для этого есть специализированные инструменты.
- Заводить Redux «на будущее» в маленьком приложении, где он не несёт пользы, а добавляет boilerplate.
