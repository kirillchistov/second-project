# Как спроектировать ленту новостей с бесконечной прокруткой?
@slug system-design-news-feed
@topic architecture
@updated 2026-10

> Ленту проектируют от требований: объём данных, частота обновлений, офлайн, доступность. Типичное решение: cursor-пагинация на API, `useInfiniteQuery` с кэшем страниц, виртуализация списка, `IntersectionObserver`-сентинел для подгрузки, оптимистичные лайки и баннер «N новых постов» вместо вставки новых записей под пальцем. Отдельно продумывают восстановление позиции прокрутки при возврате, изображения без сдвига вёрстки и доступность для клавиатуры и скринридера.

```tsx
function Feed() {
  const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
    queryKey: ['feed'],
    queryFn: ({ pageParam }) => api.feed({ cursor: pageParam, limit: 20 }),
    initialPageParam: null as string | null,
    getNextPageParam: (last) => last.nextCursor,     // курсор, а не номер страницы
  });
  const posts = data?.pages.flatMap((p) => p.items) ?? [];
  const sentinel = useInView({ rootMargin: '800px', onEnter: () => hasNextPage && !isFetchingNextPage && fetchNextPage() });

  return (
    <section aria-label="Лента" aria-busy={isFetchingNextPage}>
      <NewPostsBanner />                              {/* «3 новых поста» — по клику, без прыжка */}
      <VirtualList items={posts} estimateSize={420} render={(post) => <PostCard post={post} />} />
      <div ref={sentinel} />
    </section>
  );
}
```

План ответа на system design интервью:

1. **Требования.** Функциональные: лента, лайки, комментарии, новые посты. Нефункциональные: время до первого поста, плавность прокрутки, слабая сеть, a11y.
2. **API и модель данных.** `GET /feed?cursor=&limit=` → `{ items, nextCursor }`. Cursor стабилен при вставке новых постов, offset даёт дубликаты и пропуски.
3. **Клиентская архитектура.** Серверное состояние в TanStack Query. Нормализованные сущности, если пост обновляется в нескольких местах. Локальное UI-состояние — в компонентах.
4. **Производительность.** Виртуализация (`@tanstack/react-virtual`). Изображения с `width`/`height` или `aspect-ratio` и `loading="lazy"`. Первая страница — в SSR или с предзагрузкой.
5. **Новые данные.** Polling или SSE для счётчика новых постов. Вставка — только по действию пользователя.
6. **Взаимодействия.** Оптимистичный лайк с откатом при ошибке, дедупликация быстрых повторных нажатий.
7. **Сеть и офлайн.** Персистентный кэш, повтор при восстановлении сети, понятные состояния ошибки внутри ленты.
8. **Доступность.** `role="feed"` и `article`, корректный порядок фокуса при подгрузке, альтернатива бесконечной прокрутке — кнопка «Показать ещё».

### Подводные камни
- Вставка новых постов наверх, пока пользователь читает, сдвигает контент. Отсюда паттерн «баннер + явное действие».
- Без виртуализации тысяча карточек с изображениями превращает прокрутку в слайд-шоу и раздувает память.

- Как ранжирование на сервере влияет на cursor-пагинацию?

# Как спроектировать фронтенд чата?
@slug system-design-chat
@topic architecture
@updated 2026-10

> Ядро чата — постоянное соединение (WebSocket) для входящих событий и надёжная отправка. Каждое сообщение получает клиентский id, сразу показывается со статусом «отправляется», а сервер подтверждает его по этому id. Порядок и дедупликацию обеспечивают серверный порядковый номер или время и клиентский id. При переподключении клиент запрашивает пропущенное с последнего известного курсора. История подгружается вверх с сохранением позиции прокрутки.

```ts
type Message = { clientId: string; id?: string; chatId: string; text: string; seq?: number; status: 'sending' | 'sent' | 'failed' };

function sendMessage(chatId: string, text: string) {
  const clientId = crypto.randomUUID();
  store.upsert({ clientId, chatId, text, status: 'sending' });       // оптимистично
  socket.send({ type: 'message.send', clientId, chatId, text });
  setTimeout(() => store.markFailedIfPending(clientId), 10_000);     // нет подтверждения → «повторить»
}

socket.on('message.ack', ({ clientId, id, seq }) => store.update(clientId, { id, seq, status: 'sent' }));
socket.on('message.new', (m) => store.upsertBySeq(m));                // дубликаты по id/clientId игнорируются
socket.on('open', () => socket.send({ type: 'sync', since: store.lastSeq() })); // догнать пропущенное
```

Что разобрать на интервью:

- **Транспорт.** WebSocket — двусторонний и с низкой задержкой. SSE + `POST` проще и работает через HTTP-инфраструктуру. Long polling — запасной вариант.
- **Надёжность соединения.** Heartbeat, переподключение с экспоненциальной задержкой, синхронизация пропущенного по курсору, очередь неотправленных сообщений.
- **Состояние.** Сообщения нормализованы по чатам. Список чатов с последним сообщением и счётчиком непрочитанных. Отметки прочтения отправляются пакетно.
- **UI.** Виртуализированный список, прокрученный снизу. Подгрузка истории вверх без прыжка. «Прилипание» к низу только если пользователь уже внизу.
- **Индикаторы.** «Печатает…» с троттлингом событий и таймаутом, онлайн-статус, статусы доставки.
- **Офлайн.** Исходящие в IndexedDB, отправка при восстановлении сети, черновики по чатам.
- **Безопасность.** Аутентификация соединения, проверка доступа к каждому чату на сервере, экранирование и санитизация контента.

### Подводные камни
- Опора на порядок прихода событий по сокету: после переподключения сообщения приходят вперемешку. Сортируйте по серверному номеру.
- Автопрокрутка вниз при каждом новом сообщении, пока пользователь читает историю, выбрасывает его из контекста.

### Что спросят дальше
- Как масштабировать WebSocket-серверы и доставлять сообщение в нужный инстанс?
- Как реализовать «прочитано» без лавины запросов?

# Как сделать offline-first приложение и синхронизацию?
@slug offline-first-sync
@topic architecture
@updated 2026-10

> В offline-first приложении локальная база — источник истины для UI. Чтение идёт из IndexedDB или SQLite мгновенно, изменения сначала пишутся локально и попадают в очередь исходящих операций. Синхронизация отправляет их на сервер и подтягивает чужие изменения по курсору, когда сеть есть. Главные вопросы проектирования — разрешение конфликтов (last-write-wins, слияние по полям, CRDT) и идемпотентность повторной отправки.

```ts
// Изменение: сразу локально + операция в очередь
async function renameTask(id: string, title: string) {
  await db.transaction('rw', db.tasks, db.outbox, async () => {
    await db.tasks.update(id, { title, updatedAt: Date.now(), dirty: true });
    await db.outbox.add({ opId: crypto.randomUUID(), type: 'task.rename', id, title });
  });
  scheduleSync();
}

// Синхронизация: отправить своё, получить чужое с последнего курсора
async function sync() {
  const ops = await db.outbox.orderBy('seq').toArray();
  const { applied, changes, cursor } = await api.sync({ ops, since: await meta.get('cursor') });
  await db.transaction('rw', db.tasks, db.outbox, async () => {
    await db.outbox.bulkDelete(applied);              // сервер принял — opId идемпотентен
    for (const c of changes) await mergeTask(c);       // разрешение конфликтов
    await meta.set('cursor', cursor);
  });
}
```

Решения по слоям:

- **Хранилище.** IndexedDB (Dexie) в вебе, SQLite в мобильном. Для простых случаев — persist кэша TanStack Query, но это офлайн-чтение, а не офлайн-запись.
- **Оболочка приложения.** Service Worker кэширует HTML и ассеты, чтобы приложение открывалось без сети.
- **Очередь операций.** Отправляют операции с намерением («переименовать в X»), а не снимки состояния. Каждая имеет id, сервер применяет её идемпотентно.
- **Конфликты.** Last-write-wins прост, но теряет данные. Слияние по полям и версии сущности подходят для форм. CRDT (Yjs, Automerge) нужны для совместного редактирования текста.
- **Триггеры синхронизации.** Старт приложения, восстановление сети (`online`), фокус вкладки, периодически. Background Sync API там, где поддерживается.
- **UX.** Индикатор «не синхронизировано», понятный показ конфликтов, никаких блокирующих спиннеров на чтении.

### Подводные камни
- Время устройства ненадёжно для разрешения конфликтов: часы бывают неверными. Используйте версии или серверный порядок.
- Удаление без «надгробий» (tombstones): другой клиент, не знающий об удалении, при синхронизации «воскресит» запись.

### Что спросят дальше
- Чем CRDT отличается от операционной трансформации (OT)?
- Как мигрировать схему локальной базы у пользователей, которые давно не обновлялись?

- [Ink & Switch: Local-first software](https://www.inkandswitch.com/local-first/)
- [web.dev: Offline data](https://web.dev/learn/pwa/offline-data)

# Зачем фронтенду монорепозиторий и как его организовать?
@slug monorepo
@topic architecture
@updated 2026-10

> Монорепозиторий хранит несколько приложений и пакетов в одном репозитории: веб, мобильное приложение, API, дизайн-систему, общие типы. Плюсы — атомарные изменения сразу в библиотеке и её потребителях, единые версии зависимостей и инструменты, переиспользование без публикации пакетов. Цена — нужна инфраструктура: workspaces пакетного менеджера, оркестратор задач с кэшем (Turborepo, Nx), границы между пакетами и сборка только затронутого в CI.

```text
apps/
  web/            Vite или Next.js
  mobile/         Expo
  api/            Node
packages/
  ui/             дизайн-система
  core/           доменная логика без React
  config/         общие tsconfig, eslint
package.json      "workspaces": ["apps/*", "packages/*"]
turbo.json        граф задач: build зависит от ^build, кэш результатов
```

```json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "test": { "dependsOn": ["^build"] },
    "lint": {}
  }
}
```

Решения, которые принимают:

- **Пакетный менеджер.** pnpm workspaces строже (нет «фантомных» зависимостей) и экономнее по диску. npm и Yarn workspaces тоже подходят.
- **Сборка пакетов.** Внутренние пакеты можно не собирать, а экспортировать исходники TypeScript и отдать трансляцию приложению. Это быстрее в разработке, но требует совместимых настроек.
- **Кэш задач.** Turborepo и Nx пропускают задачи, входы которых не изменились. Remote cache делит результаты между CI и разработчиками.
- **Затронутое.** В CI запускаются только задачи пакетов, затронутых изменением, и их зависимых.
- **Границы.** Правила импорта: приложение не импортирует другое приложение, `core` не зависит от React. Проверяются линтером или тегами Nx.
- **Версии и публикация.** Changesets — для пакетов, которые публикуются наружу.

### Подводные камни
- Без кэша и запуска «только затронутого» CI с ростом репозитория занимает часы.
- Импорт из внутренних путей чужого пакета (`packages/ui/src/internal/...`) в обход `exports` разрушает границы и мешает рефакторингу.

### Что спросят дальше
- Когда монорепозиторий хуже нескольких репозиториев?
- Чем Turborepo отличается от Nx?

# Как работать с feature flags и безопасно выкатывать изменения?
@slug feature-flags
@topic architecture
@updated 2026-10

> Feature flag отделяет деплой кода от релиза функции: код уже в продакшене, но включается флагом — для команды, для 5% пользователей, для одного клиента. Это даёт постепенную выкатку, мгновенное выключение без отката деплоя, A/B-эксперименты и trunk-based разработку без долгих веток. Цена — флаги нужно удалять: каждый живой флаг удваивает число путей в коде и тестах.

```tsx
// Значения флагов вычисляются на сервере (правила, процент, сегменты) и приходят с данными пользователя
function Checkout() {
  const newPayment = useFlag('checkout.new-payment-form');   // boolean, по умолчанию false
  return newPayment ? <PaymentFormV2 /> : <PaymentForm />;
}

// Детерминированная раскатка на процент: один пользователь всегда в одной группе
function inRollout(userId: string, flag: string, percent: number) {
  return (hash(`${flag}:${userId}`) % 100) < percent;
}
```

Практики:

- **Типы флагов.** Release (временный, для выкатки), experiment (A/B), ops (kill switch для тяжёлой функции), permission (тариф или роль). Временные флаги имеют владельца и срок.
- **Вычисление на сервере.** Правила раскатки не должны утекать в бандл. Клиент получает готовые значения, при SSR — до рендера, чтобы не было мигания и ошибок гидрации.
- **Значение по умолчанию** — безопасное (выключено), если сервис флагов недоступен.
- **Постепенная выкатка**: внутренние пользователи → 1% → 10% → 50% → 100%, с мониторингом ошибок и метрик на каждом шаге.
- **Удаление.** Флаг на 100% больше недели — задача на удаление ветки кода. Линтер или отчёт находит устаревшие флаги.
- **Стандарт.** OpenFeature даёт единый API поверх разных провайдеров (LaunchDarkly, Unleash, GrowthBook, свой сервис).

### Подводные камни
- Флаг, вычисляемый на клиенте после загрузки, вызывает мигание старого интерфейса и расхождение с SSR.
- Вложенные и зависящие друг от друга флаги порождают комбинации, которые никто не тестировал.

### Что спросят дальше
- Как провести A/B-тест и не испортить метрики эффектом новизны?
- Чем canary-релиз отличается от раскатки флагом?

### Ссылки
- [Martin Fowler: Feature Toggles](https://martinfowler.com/articles/feature-toggles.html)
- [OpenFeature](https://openfeature.dev/)

# Как поддерживать TypeScript в большом проекте: строгость, миграция, скорость?
@slug typescript-at-scale
@topic typescript
@updated 2026-10

> В большом проекте TypeScript должен быть строгим и быстрым. Строгость: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, запрет `any` линтером, типизированные границы (схемы для внешних данных). Миграцию с JS или со слабых настроек делают постепенно: правила включают по папкам, долг отслеживают метрикой. Скорость дают project references и инкрементальная сборка, отказ от тяжёлых вычисляемых типов и проверка типов отдельно от сборки бандлера.

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,          // arr[i] имеет тип T | undefined
    "exactOptionalPropertyTypes": true,        // { x?: string } не принимает x: undefined
    "noImplicitOverride": true,
    "verbatimModuleSyntax": true,              // import type там, где только типы
    "isolatedModules": true,                   // совместимость с esbuild/swc/Rolldown
    "composite": true,
    "incremental": true
  },
  "references": [{ "path": "../core" }, { "path": "../ui" }]
}
```

Что спросят:

- **Постепенная миграция.** `allowJs` + `checkJs` по файлам, переименование в `.ts` снизу вверх по графу зависимостей. Счётчик `any` и `@ts-expect-error` в CI не должен расти.
- **`@ts-expect-error` вместо `@ts-ignore`.** Первый упадёт, когда ошибку исправят, и напомнит удалить комментарий.
- **Project references** делят проект на независимо проверяемые части: `tsc -b` перепроверяет только изменившееся.
- **Медленные типы.** Глубокие условные и рекурсивные типы, огромные объединения и вывод из больших объектов замедляют IDE. Измеряют через `--extendedDiagnostics` и `--generateTrace`.
- **Сборка и проверка раздельно.** Vite и esbuild только транслируют. Типы проверяет `tsc --noEmit` в CI и в редакторе.
- **Новые версии.** TypeScript 7 (компилятор, переписанный на Go) многократно ускоряет проверку, но требует проверить совместимость инструментов.

### Подводные камни
- Включение `strict` одним коммитом на большом проекте даёт тысячи ошибок, а их «починка» через `as any` хуже исходного состояния.
- Типы, «доказанные» через `as`, расходятся с реальными данными. Утверждения должны быть редкими и обоснованными.

### Что спросят дальше
- Как найти, какой тип замедляет проверку?
- Чем `noUncheckedIndexedAccess` полезен и почему он не входит в `strict`?

### Ссылки
- [TypeScript: TSConfig Reference](https://www.typescriptlang.org/tsconfig/)
- [TypeScript: Project References](https://www.typescriptlang.org/docs/handbook/project-references.html)

# Как бороться с нестабильными (flaky) тестами?
@slug flaky-tests
@topic testing
@updated 2026-10

> Флаки-тест то проходит, то падает без изменений в коде. Он хуже отсутствия теста: команда привыкает перезапускать CI и пропускает настоящие падения. Типичные причины: ожидание по таймауту вместо состояния, общее состояние между тестами, зависимость от порядка запуска, реальные время, сеть и случайность, гонки анимаций. Лечат воспроизведением (повторный прогон, тот же seed), устранением причины и карантином с владельцем и сроком, а не бесконечными ретраями.

```ts
// Флаки: ожидание временем и проверка один раз
await page.click('text=Сохранить');
await page.waitForTimeout(1000);
expect(await page.locator('.toast').isVisible()).toBe(true);

// Стабильно: ждём состояние, которое видит пользователь
await page.getByRole('button', { name: 'Сохранить' }).click();
await expect(page.getByRole('status')).toHaveText('Сохранено');

// Unit: время и случайность под контролем
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-03-01T10:00:00Z'));
const random = seededRandom(42);
```

Процесс:

1. **Обнаружить.** CI отмечает тесты, которые прошли только после повтора. Отчёт о самых нестабильных тестах ведётся постоянно.
2. **Воспроизвести.** Прогон в цикле (`--repeat-each=50` в Playwright, `--retries=0`), случайный порядок с фиксированным seed, медленная машина или CPU throttling.
3. **Найти класс причины:**
   - **время** — фейковые таймеры, фиксированная таймзона и локаль в CI;
   - **общее состояние** — сброс моков, хранилища, MSW-обработчиков и кэша QueryClient между тестами;
   - **данные** — уникальные данные на тест, а не общий «тестовый пользователь»;
   - **асинхронность** — `findBy`, `waitFor`, web-first проверки вместо `sleep`;
   - **окружение** — внешние сервисы заменены моками, анимации отключены.
4. **Карантин** — временно исключить тест с задачей, владельцем и сроком. Без срока карантин превращается в кладбище.
5. **Ретраи** в CI — только как сигнал (тест помечается нестабильным), а не как способ «позеленить» сборку.

### Подводные камни
- Увеличение таймаутов «пока не перестанет падать» прячет гонку и замедляет весь набор тестов.
- Тесты, проходящие только в определённом порядке, ломаются при включении параллельного запуска.
