# Как читать потоковый ответ fetch через ReadableStream?
@slug fetch-streaming
@topic fullstack

> `response.body` — это `ReadableStream` байтов: его можно читать по частям через `getReader()`, не дожидаясь, пока придёт весь ответ целиком. Это нужно для прогресс-бара загрузки большого файла, построчной обработки NDJSON или вывода токенов LLM по мере генерации — везде, где ждать полный ответ дорого или бессмысленно.

```tsx
const res = await fetch('/api/export.csv');
const reader = res.body!.getReader();
const decoder = new TextDecoder();
let text = '';

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  text += decoder.decode(value, { stream: true });
  updateProgress(text.length);
}
```

Для потока текстовых чанков, разделённых переводом строки (частый формат для стриминга LLM-ответов), поток дополнительно пропускают через `TextDecoderStream` и `ReadableStream.pipeThrough` с построчным трансформом, чтобы получать уже готовые куски, а не разбирать границы вручную. Общий размер ответа для процента прогресса берут из заголовка `Content-Length`, если сервер его присылает — для чанкованной передачи (`Transfer-Encoding: chunked`) этого заголовка может не быть.

### Подводные камни
- Декодировать каждый чанк как самостоятельную строку без `{ stream: true }` — многобайтовый UTF-8 символ может оказаться разрезан между чанками и декодируется с ошибкой.
- Ждать `response.json()` там, где нужен именно построчный поток — это читает весь поток разом, теряя смысл стриминга.

# Как передавать бинарные данные по WebSocket?
@slug websocket-binary-data
@topic fullstack

> По умолчанию `ws.send()` принимает строку, но WebSocket умеет передавать и бинарные данные — `Blob` или `ArrayBuffer`. Свойство `ws.binaryType` определяет, в каком виде придут входящие бинарные сообщения: `'blob'` (по умолчанию) или `'arraybuffer'`, если нужна синхронная обработка байтов без промежуточного чтения `Blob` через `FileReader`.

```tsx
ws.binaryType = 'arraybuffer';
ws.onmessage = (event) => {
  if (event.data instanceof ArrayBuffer) {
    const view = new Uint8Array(event.data);
    // разбор бинарного протокола, например заголовок + payload
  }
};

const buffer = new TextEncoder().encode(JSON.stringify(payload));
ws.send(buffer);
```

Бинарный формат (например, Protocol Buffers или собственный компактный бинарный протокол) выбирают, когда объём трафика критичен — JSON многословен для часто отправляемых небольших сообщений типа координат курсора или аудиоданных. Обратная сторона — бинарный протокол сложнее отлаживать: его не прочитать глазами во вкладке Network, нужны специальные инструменты или логирование декодированного вида.

### Подводные камни
- Не выставить `binaryType = 'arraybuffer'`, ожидая его, и получить `Blob`, с которым нельзя работать синхронно.
- Выбрать бинарный протокол там, где трафик не критичен — потеря отлаживаемости без реальной выгоды.

# Как масштабировать WebSocket-сервер на несколько инстансов?
@slug websocket-scaling
@topic fullstack
@verified react@19.3
@updated 2026-11

> Живой TCP-сокет нельзя перенести на другой процесс — он физически открыт на конкретном инстансе, и балансировщик, в отличие от обычного HTTP-запроса, не может перенаправить его на любой свободный сервер, не разорвав. Sticky sessions (балансировщик по cookie или IP всегда ведёт клиента на тот же инстанс) решают, куда попадёт реконнект, а не то, как доставить клиенту событие, рождённое на другом инстансе — для этого нужен pub/sub-брокер между инстансами.

Главная сложность — сообщение, предназначенное клиенту A, может понадобиться отправить с инстанса, где A не подключён, если его туда направил балансировщик для другого запроса (например, REST-вызов от другого пользователя). Решают это через pub/sub-брокер (Redis Pub/Sub, NATS): инстанс, получивший событие, публикует его в канал, а инстанс, где реально открыто соединение с нужным клиентом, подписан на этот канал и пересылает сообщение в сокет.

### Подводные камни
- Полагаться только на sticky sessions без пути для доставки «чужих» событий — при рестарте или ребалансировке инстанса соединения клиентов этого инстанса обрываются разом.
- Не учитывать, что состояние «кто куда подключён» само по себе нужно где-то хранить и синхронизировать между инстансами.

# Что такое backpressure и порядок сообщений в WebSocket?
@slug websocket-backpressure
@topic fullstack

> Backpressure — ситуация, когда отправитель шлёт сообщения быстрее, чем получатель (или сеть) успевает их обрабатывать: буфер отправки растёт, потребление памяти увеличивается, а задержка доставки накапливается. `ws.bufferedAmount` на клиенте показывает, сколько байт ещё не отправлено в сеть — большое и растущее значение сигнализирует, что стоит замедлить отправку или начать отбрасывать неважные сообщения (например, частые обновления позиции курсора).

```tsx
function send(data: string) {
  if (ws.bufferedAmount > 1_000_000) return; // пропускаем, канал и так перегружен
  ws.send(data);
}
```

Порядок сообщений в рамках одного TCP-соединения (а WebSocket работает поверх TCP) гарантирован — сообщения приходят в том порядке, в котором их отправили. Проблема возникает не с порядком внутри одного соединения, а при переподключении: пока клиент реконнектится, он может пропустить сообщения, отправленные сервером в этот промежуток, если протокол не предусматривает способ досылки пропущенного.

### Подводные камни
- Слать поток высокочастотных обновлений без проверки `bufferedAmount` — буфер растёт, задержка накапливается, UI получает устаревшие данные с опозданием.
- Путать гарантию порядка внутри соединения с гарантией доставки через разрывы — это разные вещи.

# Как нормализовать вложенные отношения через EntityAdapter и писать кастомные селекторы поверх него?
@slug rtk-entity-adapter-relations
@topic state

> `createEntityAdapter` сам по себе нормализует только одну коллекцию (`{ ids, entities }`), но реальные данные обычно связаны: у поста есть автор, у задачи — исполнитель. Вложенные отношения нормализуют так же, как и верхний уровень — отдельными адаптерами для каждой сущности (`usersAdapter`, `postsAdapter`), а связь хранят через id, а не вложенный объект: `post.authorId`, а не `post.author`.

```tsx
const selectPostWithAuthor = createSelector(
  [postsAdapter.getSelectors((s: RootState) => s.posts).selectById,
   usersAdapter.getSelectors((s: RootState) => s.users).selectEntities,
   (_: RootState, id: string) => id],
  (post, usersById) => post ? { ...post, author: usersById[post.authorId] } : undefined,
);
```

Собирать «денормализованный» вид (пост вместе с объектом автора) нужно в мемоизированном селекторе, а не в самом state — так обновление профиля автора в одном месте (`usersSlice`) автоматически отражается во всех постах этого автора без дублирования и рассинхронизации данных в двух местах одновременно.

### Подводные камни
- Хранить вложенный объект автора прямо внутри поста — при обновлении имени автора нужно находить и чинить его во всех постах.
- Писать `createSelector` с параметром (`id`) неаккуратно — у параметризованных селекторов своя специфика мемоизации, кэш на один `id` может вытеснять кэш на другой.

# Чем RTK Query отличается от TanStack Query и как выбрать?
@slug rtk-query-vs-tanstack-query
@topic state

> Обе библиотеки решают одну и ту же задачу — кэширование серверного состояния, инвалидация, повторные запросы — но RTK Query построен поверх Redux и хранит кэш в Redux store, а TanStack Query не зависит от стейт-менеджера и работает сама по себе. Если в проекте уже есть Redux для клиентского состояния, RTK Query логично ложится рядом, используя тот же store, DevTools и паттерны. Если Redux в проекте нет и не нужен, тянуть его только ради RTK Query избыточно — TanStack Query самодостаточна.

Инвалидация кэша у RTK Query построена на явных тегах (`providesTags`/`invalidatesTags`), которые нужно расставить вручную и согласованно. TanStack Query чаще инвалидируют по ключам запроса (`queryKey`) через `invalidateQueries`, что местами гибче (можно инвалидировать по префиксу ключа), но требует той же дисциплины в проектировании ключей. По возможностям — бесконечная прокрутка (`useInfiniteQuery`), параллельные и зависимые запросы, отмена — обе библиотеки покрывают схожий набор сценариев, различия чаще в деталях API и экосистеме вокруг.

### Подводные камни
- Подключать Redux только ради RTK Query в проекте без другого клиентского состояния — лишняя зависимость и concept count.
- Использовать обе библиотеки одновременно без чёткого разделения ответственности — два независимых кэша для одних и тех же данных рассинхронизируются.
