# Что такое React и какие задачи он решает?
@slug what-is-react
@topic basics
@legacy 1

> React — библиотека для построения пользовательских интерфейсов из компонентов. Вы декларативно описываете, как UI выглядит при данном состоянии, а React сам вычисляет минимальные изменения и применяет их к DOM (или к нативным view в React Native).

Ключевые идеи React:

- **Компоненты.** UI собирается из небольших переиспользуемых функций, которые принимают данные (props) и возвращают разметку.
- **Декларативность.** Вы описываете *что* должно быть на экране, а не *как* по шагам менять DOM. Это сильно упрощает работу со сложным состоянием.
- **Однонаправленный поток данных.** Данные идут сверху вниз через props, изменения — через явные обновления состояния. Поведение предсказуемо и легко отлаживается.
- **Независимость от платформы.** Ядро `react` ничего не знает о браузере: рендереры `react-dom`, `react-native` и другие применяют результат к конкретной среде.

```tsx
function Greeting({ name }: { name: string }) {
  return <h1>Привет, {name}!</h1>;
}
```

Чем React **не** является: это не полноценный фреймворк «всё в одном». Роутинг, работа с данными, сборка и SSR решаются отдельными инструментами или фреймворками поверх React (Next.js, React Router, TanStack Start). Команда React сама рекомендует начинать новые проекты с фреймворка или с Vite.

Ограничения, о которых стоит сказать честно: много решений приходится выбирать самому (стейт-менеджер, стили, формы), а модель рендеринга и правила хуков требуют времени на освоение.

### Подводные камни
- Называть React фреймворком без оговорок — на собеседовании лучше показать, что вы понимаете разницу между библиотекой и метафреймворком.
- Говорить, что React «быстрее DOM», — Virtual DOM не делает приложение быстрее ручной работы с DOM, он делает быстрым *достаточно* декларативный код.

# Что такое JSX и во что он компилируется?
@slug jsx
@topic basics
@legacy 4

> JSX — расширение синтаксиса JavaScript, позволяющее писать разметку прямо в коде. Браузер его не понимает: компилятор (Babel, SWC, esbuild, TypeScript) превращает JSX в вызовы `jsx()` из `react/jsx-runtime`, которые создают обычные JS-объекты — React-элементы.

```tsx
// Исходный код
const el = <button className="primary" onClick={save}>Сохранить</button>;

// Примерно так это выглядит после компиляции (новый JSX transform, React 17+)
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx('button', { className: 'primary', onClick: save, children: 'Сохранить' });
```

До React 17 JSX компилировался в `React.createElement(...)`, поэтому в каждом файле нужен был `import React from 'react'`. С новым JSX transform этот импорт не обязателен.

Правила JSX:

- Компонент возвращает **один корневой элемент** (или фрагмент `<>...</>`).
- Все теги закрыты: `<img />`, `<br />`.
- Атрибуты в camelCase: `className`, `htmlFor`, `onClick`, `tabIndex`.
- В фигурных скобках `{}` — любое JS-*выражение*, но не инструкция (`if`, `for` писать нельзя, используйте тернарник, `&&` или `map`).
- Имена компонентов — с заглавной буквы: `<Button />` — компонент, `<button />` — HTML-тег.

JSX по умолчанию экранирует значения в `{}`, поэтому вставка пользовательской строки безопасна от XSS (в отличие от `dangerouslySetInnerHTML`).

### Подводные камни
- `{count && <Badge />}` при `count === 0` отрендерит `0`. Используйте `count > 0 && ...`.
- Компонент с маленькой буквы React воспримет как HTML-тег.

# Компонент, элемент и экземпляр — в чём разница?
@slug component-vs-element
@topic basics

> Компонент — функция (или класс), которая описывает часть UI. Элемент — неизменяемый объект `{ type, props, key }`, который возвращает JSX и который описывает, *что* отрендерить. Экземпляр — «живая» копия компонента в дереве со своим состоянием; у функциональных компонентов его роль играет внутренний Fiber-узел.

```tsx
function Avatar({ src }: { src: string }) {   // компонент
  return <img src={src} alt="" />;
}

const element = <Avatar src="/me.png" />;    // элемент: { type: Avatar, props: { src: ... } }
```

Элемент — это просто описание. Создать элемент не значит отрендерить компонент: React вызовет функцию `Avatar` только когда элемент попадёт в дерево.

Каждое место, где компонент рендерится, получает **своё состояние**. Два `<Counter />` рядом — это два независимых счётчика, хотя функция одна.

Состояние привязано не к функции и не к переменной, а к **позиции в дереве**. Если на том же месте остаётся элемент того же типа, состояние сохраняется; если тип меняется — поддерево пересоздаётся.

### Подводные камни
- Объявлять компонент внутри другого компонента: при каждом рендере создаётся новая функция, то есть новый тип, и React размонтирует поддерево, теряя состояние и фокус.

# Что такое props и почему их нельзя менять?
@slug props
@topic basics
@legacy 6

> Props — входные параметры компонента, которые передаёт родитель. Они доступны только для чтения: компонент должен вести себя как чистая функция от своих props. Если данные должны меняться, это state — у компонента или у родителя, который передаст новые props.

```tsx
type CardProps = {
  title: string;
  variant?: 'default' | 'accent';
  children: React.ReactNode;
};

function Card({ title, variant = 'default', children }: CardProps) {
  return (
    <section className={`card card--${variant}`}>
      <h2>{title}</h2>
      {children}
    </section>
  );
}

<Card title="Профиль">
  <p>Любой JSX попадает в props.children</p>
</Card>
```

Важные детали:

- **`children`** — особый prop: всё, что вложено между тегами компонента. Это основа композиции.
- **Значения по умолчанию** задаются через деструктуризацию (`variant = 'default'`). `defaultProps` для функциональных компонентов удалён в React 19.
- **Функции в props** — способ передать «колбэк» наверх: ребёнок вызывает `onChange`, а состояние меняет родитель.
- **`key` и `ref`** — не обычные props (`key` вообще не попадает в компонент). В React 19 `ref` передаётся как обычный prop функциональным компонентам.

Почему props нельзя мутировать: React сравнивает старые и новые значения по ссылке. Мутация объекта, полученного от родителя, ломает это сравнение и делает поведение непредсказуемым.

### Подводные камни
- Копировать props в state «на всякий случай» (`useState(props.value)`) — state не обновится, когда родитель передаст новое значение.
- Передавать огромные объекты «целиком» без нужды — сложнее мемоизировать и понимать зависимости.

# Что такое state и чем он отличается от props?
@slug state-vs-props
@topic basics
@legacy 12

> State — «память» компонента: данные, которые меняются со временем и при изменении вызывают повторный рендер. Props приходят снаружи и только читаются; state принадлежит самому компоненту, и изменить его можно только через функцию обновления.

| | props | state |
|---|---|---|
| Откуда | от родителя | создаётся внутри компонента |
| Кто меняет | родитель | сам компонент через `setState` |
| Изменение вызывает рендер | да (рендер родителя) | да |

```tsx
function Counter({ step }: { step: number }) {      // step — prop
  const [count, setCount] = useState(0);            // count — state
  return <button onClick={() => setCount(count + step)}>{count}</button>;
}
```

Почему нельзя просто использовать переменную `let count = 0`: локальная переменная не сохраняется между рендерами (функция вызывается заново), а её изменение не сообщает React, что нужно перерисовать UI.

Хорошее правило: в state кладут только то, что **нельзя вычислить** из props или другого state. Всё остальное считают прямо во время рендера.

```tsx
// Плохо: дублирование и рассинхронизация
const [fullName, setFullName] = useState('');
useEffect(() => setFullName(first + ' ' + last), [first, last]);

// Хорошо: производное значение
const fullName = `${first} ${last}`;
```

### Подводные камни
- Хранить в state производные данные и синхронизировать их эффектом — лишний рендер и риск рассинхронизации.
- Ожидать, что `count` изменится сразу после `setCount` — значение обновится только в следующем рендере.

# Как работает useState и почему новое значение «не видно» сразу?
@slug use-state
@topic hooks
@legacy 36

> `useState(initial)` возвращает пару `[value, setValue]`. Вызов `setValue` не меняет переменную в текущем рендере — он ставит обновление в очередь и планирует новый рендер. Каждый рендер видит свой «снимок» состояния. Чтобы обновить на основе предыдущего значения, передают функцию: `setCount(c => c + 1)`.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    console.log(count); // 0 — это снимок текущего рендера
  }
  // После клика count станет 1, а не 2: оба вызова считают от 0

  function handleClickCorrect() {
    setCount((c) => c + 1);
    setCount((c) => c + 1); // теперь 2: функции применяются по очереди
  }
  // ...
}
```

Особенности `useState`:

- **Ленивая инициализация.** `useState(() => expensiveInit())` вызовет функцию только при первом рендере. А `useState(expensiveInit())` — при каждом.
- **Сравнение через `Object.is`.** Если новое значение равно текущему, React может пропустить рендер.
- **Батчинг.** Несколько обновлений в одном обработчике (и, начиная с React 18, в промисах и таймаутах) объединяются в один рендер.
- **Замена, а не слияние.** В отличие от `this.setState` в классах, `setState` хука заменяет объект целиком — нужно копировать поля самому.

### Подводные камни
- Мутировать объект и передавать тот же объект в `setState` — `Object.is` вернёт `true`, и рендера не будет.
- Вызывать `setState` прямо в теле компонента без условия — бесконечный цикл рендеров.

# Как правильно обновлять объекты и массивы в state?
@slug immutable-updates
@topic basics
@legacy 31

> Иммутабельно: создавать новый объект или массив вместо изменения существующего. React сравнивает state по ссылке (`Object.is`), поэтому мутация не будет замечена, а ещё она ломает мемоизацию, Strict Mode и инструменты вроде time-travel.

```tsx
const [user, setUser] = useState({ name: 'Аня', address: { city: 'Казань' } });

// Объект: копируем каждый уровень, который меняем
setUser((u) => ({ ...u, address: { ...u.address, city: 'Пермь' } }));

// Динамический ключ — вычисляемое имя свойства
function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setForm((f) => ({ ...f, [e.target.name]: e.target.value }));
}

// Массивы
setItems((xs) => [...xs, newItem]);                        // добавить
setItems((xs) => xs.filter((x) => x.id !== id));           // удалить
setItems((xs) => xs.map((x) => (x.id === id ? { ...x, done: true } : x))); // изменить
setItems((xs) => xs.toSorted((a, b) => a.price - b.price)); // сортировка без мутации
```

Методы, которые **мутируют** массив и не подходят для state напрямую: `push`, `pop`, `splice`, `sort`, `reverse`, присваивание по индексу. Для них есть иммутабельные аналоги: `toSorted`, `toReversed`, `toSpliced`, `with` (ES2023).

Для глубоко вложенных структур удобна библиотека **Immer** (`useImmer` или встроенная в Redux Toolkit): вы пишете «мутирующий» код, а получаете новый объект. Но часто лучше просто сделать структуру state более плоской.

### Подводные камни
- Спред копирует только один уровень: `{ ...user }` всё ещё разделяет `user.address` с оригиналом.
- `sort()` мутирует исходный массив, даже если результат кладётся в `setState`.

# Что такое Virtual DOM и reconciliation?
@slug virtual-dom
@topic rendering
@legacy 5

> Virtual DOM — описание UI в виде дерева JS-объектов (React-элементов). При обновлении React строит новое дерево, сравнивает его с предыдущим (reconciliation, «согласование») и применяет к настоящему DOM только необходимые изменения.

Процесс обновления в общих чертах:

1. **Trigger** — что-то вызвало обновление (`setState`, новый контекст, рендер родителя).
2. **Render** — React вызывает компоненты и получает новое дерево элементов.
3. **Reconciliation** — сравнивает новое дерево со старым и вычисляет разницу.
4. **Commit** — применяет изменения к DOM, затем запускает эффекты.

Полное сравнение двух деревьев — задача O(n³). React использует эвристики и получает O(n):

- элементы **разных типов** дают разные поддеревья — старое удаляется целиком;
- элементы списка сопоставляются по **`key`**.

Важная мысль для собеседования: Virtual DOM — не «магия скорости». Ручная точечная работа с DOM всегда может быть быстрее. Ценность в том, что вы пишете декларативный код, а React делает обновления *достаточно* эффективными. Фреймворки вроде Svelte и Solid вообще обходятся без Virtual DOM, используя компиляцию и сигналы.

Термин «Virtual DOM» сейчас в документации React почти не используется — говорят о дереве рендера, reconciliation и Fiber.

### Подводные камни
- Путать рендер и обновление DOM: компонент может отрендериться, но если результат не изменился, DOM не трогается.

# Зачем нужен key и почему индекс — плохой ключ?
@slug keys
@topic rendering
@legacy 14

> `key` помогает React сопоставить элементы списка между рендерами: какой элемент добавлен, удалён или переставлен. Ключ должен быть стабильным и уникальным среди соседей — обычно это id из данных. Индекс массива ломается при вставке, удалении и сортировке: состояние и DOM «переезжают» к чужим элементам.

```tsx
<ul>
  {todos.map((todo) => (
    <TodoItem key={todo.id} todo={todo} />
  ))}
</ul>
```

Что происходит с `key={index}` при удалении первого элемента: элемент с индексом 0 теперь — бывший второй. React считает, что изменились props у существующих компонентов, а последний удалён. Если в `TodoItem` есть локальный state (например, текст в инпуте или флаг «редактируется»), он останется на старой позиции и окажется у другого элемента.

Индекс допустим, если список **статичен**: не сортируется, не фильтруется и элементы не имеют своего состояния.

`key` полезен и вне списков: смена ключа заставляет React **пересоздать** компонент со свежим состоянием.

```tsx
<ProfileForm key={userId} userId={userId} />  // сброс формы при смене пользователя
```

### Подводные камни
- `key={Math.random()}` или `crypto.randomUUID()` в рендере — компоненты пересоздаются при каждом рендере.
- Ключ ставится на элемент внутри `map`, а не внутри дочернего компонента.
- `key` не передаётся в props — если нужен id, передайте его отдельно.

# Условный рендеринг и списки: какие есть приёмы и ловушки?
@slug conditional-rendering
@topic basics

> Условия в JSX пишут через тернарный оператор, `&&` или ранний `return`; списки — через `map` с `key`. Основные ловушки: `0` и `NaN` при использовании `&&`, сложные вложенные тернарники и фильтрация, которая теряет ключи.

```tsx
function Inbox({ messages, loading }: Props) {
  if (loading) return <Spinner />;                 // ранний return

  return (
    <>
      {messages.length > 0 && <Badge count={messages.length} />}  {/* не messages.length && */}
      {messages.length === 0 ? (
        <Empty />
      ) : (
        <ul>
          {messages.map((m) => (
            <li key={m.id}>{m.subject}</li>
          ))}
        </ul>
      )}
    </>
  );
}
```

Что важно помнить:

- `false`, `null`, `undefined` и `true` в JSX ничего не рендерят, а `0` и `NaN` — рендерят.
- Компонент может вернуть `null`, чтобы ничего не показывать (но хуки внутри всё равно должны вызываться до этого `return`).
- Вложенные тернарники лучше вынести в переменную или отдельный компонент.
- Условие, меняющее **тип** элемента в одной позиции, сбрасывает состояние поддерева.

```tsx
// Состояние Form сбросится при переключении isEdit,
// потому что на этом месте разные типы
{isEdit ? <EditForm /> : <ViewForm />}
```

### Подводные камни
- `{items.length && <List />}` выводит `0` для пустого списка.
- Хук после условного `return` нарушает правила хуков.
