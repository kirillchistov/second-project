# Аудит архитектуры и кода — 7 ноября 2026

Смотрел монорепо целиком: как контент становится объектами, где живёт логика без UI, как устроены веб, демо, мобильное приложение и API, и что из этого реально проверяют тесты. Это не построчное ревью каждого экрана. Ниже — решения, которые держат проект, и места, где структура уже расходится с тем, как код устроен на самом деле.

## Короткий вывод

Деление на пакеты выбрано удачно и в коде соблюдается. `packages/content` — тексты и схемы, `packages/core` — чистые функции (проверка ответа, SRS, путь, XP, оценка по рубрике), приложения только показывают и хранят. Из-за этого веб, Expo и Hono не тащат друг другу UI.

Слабее два шва. Первый: один и тот же урок нарисован дважды, в `apps/web/src/demo/exercises` и `apps/mobile/src/components/exercises`, и общая часть — только `checkAnswer`. Второй: тесты контента проверяют форму (180 вопросов, уникальные slug, закрытые код-фенсы, индекс ответа в диапазоне) и не проверяют, что пример в вопросе согласован с упражнением. Контентный аудит как раз нашёл такие расхождения, и CI их пропускает.

## Как устроено

```text
packages/content   Markdown-вопросы, YAML-упражнения, рубрики, Zod
packages/core      проверка ответов, SRS, сессия урока, грейдер баллов
apps/web           Vite SPA: каталог, тренировка, мок-собеседование
apps/web demo      тот же бинарь, mode=pages: уроки в браузере, localStorage
apps/mobile        Expo Router, SQLite, те же уроки
apps/api           Hono: аккаунты, синхронизация прогонов, форум, ИИ-оценка
```

Сборка вопросов не зависит от бандлера. `buildQuestions` принимает словарь «путь → текст», веб отдаёт туда `import.meta.glob`, Node — файлы с диска, мобильное приложение — JSON из `npm run bundle:content`. Нумерация — уровень, затем имя файла, затем порядок в файле. Это простой контракт, его легко сломать только переименованием.

Упражнение — размеченное объединение из семи типов. Схема ловит ответ за пределами вариантов, дырку `___` без токена, строку бага длиннее файла и повторяющиеся подписи. Черновики генератора проверяются тем же парсером и не имеют права пересекаться с банком по id.

Оценка устного ответа устроена так, что модель не ставит балл. `apps/api/src/examiner.ts` просит Claude отметить пункты рубрики (`covered` / `partial` / `missing`) и список фактических ошибок. Число и вердикт считает `packages/core`. Повтор одного и того же размеченного ответа даёт тот же балл. Это правильная граница: промпт можно менять, шкала остаётся в коде и в тестах.

Аккаунты без внешнего провайдера. Пароль — scrypt с параметрами в самой строке хэша (`N`, `r`, `p`, соль), сравнение через `timingSafeEqual`. Для несуществующего email считается заранее подготовленный пустой хэш, чтобы по времени не отличить «нет такого пользователя». Сессия — 32 случайных байта, клиенту уходит токен, в базе SHA-256. Веб держит его в cookie `HttpOnly` + `SameSite=Lax`, мобильное приложение — в `Authorization: Bearer`. Форум хранит исходный Markdown и просит клиентов показывать его текстом, не HTML.

Демо для GitHub Pages включается режимом Vite `pages`: плагин подменяет точку входа на `demo/main.tsx`, обычная сборка этот граф не тянет. Два продукта в одном `apps/web` при этом не смешивают бандлы. Это аккуратнее, чем флаг времени выполнения.

## Что уже хорошо

- Доменная логика урока не скопирована в приложения. И веб-демо, и мобильное приложение вызывают `checkAnswer`, `review`, `lessonXp`, `shuffle` из `@rr/core`. Расхождение «на телефоне засчитали, на сайте нет» этим закрыто.
- `checkAnswer` разбирает ответ по дискриминанту `kind` и типу упражнения. Перепутать индекс quiz с номером строки бага типы не дают.
- Грейдер, SRS, интервью-подборка и синхронизация прогонов покрыты модульными тестами в `packages/core` и `apps/api`. Для чистого ядра этого достаточно.
- CSRF для cookie-запросов: не-GET без Bearer отвергается, если `Origin` есть и он не из `allowedOrigins`. Вместе с `SameSite=Lax` кросс-сайтовая отправка cookie и так не проходит. Bearer-клиенту проверка не мешает, потому что браузер сам такой заголовок на чужой сайт не поставит.
- Линт — oxlint на всё монорепо, типы — `tsc -b` после сборки контентного бандла. `npm run check` связывает это с тестами. Секреты модели остаются на API: в клиентский бандл ключ не импортируется.

## Где структура уже трещит

### Два отрисовщика одного урока

`ChoiceExercise`, `FindBugExercise`, `FillTokensExercise`, `ArrangeExercise`, `CardExercise`, `ReorderList` существуют парами: DOM в `apps/web/src/demo/exercises` и React Native в `apps/mobile/src/components/exercises`. Сверка ответов общая, состояние «выбрал / показал / перемешал» — нет. Перемешивание в вебе — `useShuffledOrder`, на телефоне — `useShuffled`. Пока они оба зовут `shuffle` из core, порядок совпадает. Любое новое правило («после ошибки подсветить не только выбранное, но и верное», «в find-bug можно тыкать несколько строк») придётся вносить дважды, и тест этого не увидит: компонентных тестов на эти экраны нет, есть только `Markdown.test.tsx` и тесты прогресса демо.

Выносить общий React-компонент некуда: рендереры разные. Имеет смысл вынести не JSX, а состояние карточки: что выбрано, можно ли ещё отвечать, какой индекс верный после shuffle. Тонкий хук или чистая функция в `@rr/core` оставит в приложениях только разметку.

### Каталог и уроки — два клиента одного банка, и это пока не названо в схеме репозитория

README рисует веб как «Vite SPA, загрузка вопросов через import.meta.glob» и мобильное приложение как будущее. Фактически веба два (каталог собеседования и путь уроков), мобильное приложение уже ходит в тот же банк через `content.json`, а API читает вопросы и рубрики с диска при старте. Четыре потребителя. Контракт у них один — типы `@rr/content`, — но версии разъезжаются молча: веб в dev читает Markdown напрямую, телефон читает последний закоммиченный или локально собранный JSON. Если забыть `npm run bundle:content` перед сборкой телефона, банк на устройстве старее веба, и тесты веба этого не покажут.

Стоит в `npm run check` для мобильной сборки требовать свежий бандл или генерировать его в `prebuild`, а не полагаться на то, что человек помнит скрипт. `npm run build` веба бандл уже пересобирает; у `apps/mobile` такого крюка в корневом `package.json` нет.

### Документация структуры отстаёт от файлов

`README` пишет «вопросы: `junior-1.md` … `senior-4.md`» и «React 19.2». Файлы доходят до `junior-4`, `middle-8`, `senior-8`, а проверенные вопросы помечены `react@19.3` и `next@16.4`. Для репозитория, в котором контент и есть продукт, эта страница — часть интерфейса. Её стоит править в том же изменении, что и новый файл вопросов.

### Проверка контента не про то, что ломает ученика

`packages/content/src/content.test.ts` проверяет количество по уровням (32 / 82 / 66), kebab-case slug, длину краткого ответа и тела, https-ссылки, чётность код-фенсов, формат `@verified`. `exercises.test.ts` проверяет уникальность id и что `question:` указывает на существующий slug.

Этого мало для банка, который засчитывает ответ автоматически. Пример в `fetch-retry-backoff` возвращает 429 без повтора, а карточка на тот же вопрос считает это ошибкой. Оба файла проходят тесты. Порог `body.length > 200` пропускает `when-not-redux` (366 символов) и `rtk-query-polling` (389) как полноценные вопросы.

Имеет смысл добавить два дешёвых инварианта, не пытаясь проверить факты автоматикой:

- у каждого вопроса ровно одна quiz-карточка, и её `explanation` не противоречит шаблону, который вы готовы поддерживать вручную (хотя бы список slug, у которых пример кода и find-bug разбирают одну и ту же строку);
- прогон 36 predict-output: выполнить сниппет и сравнить вывод с отмеченным вариантом. Для чистого JS (промисы, event loop) это Node. Для React-порядка — маленький jsdom-харнесс. Схема Zod здесь бессильна.

Пока этого нет, ревью контента остаётся ручным, и новые короткие карточки (RTK, WebSocket, fetch) проходят в банк легче, чем старые разборы.

### ИИ-квота и лимиты живут в памяти процесса

В `createApp` суточный лимит проверок — `Map` по ключу `дата:user` или `дата:device`. Заголовок `x-device-id` присылает клиент. Без аккаунта смена заголовка обнуляет квоту. `RateLimiter` форума устроен так же: окно хитов в памяти, после рестарта и на втором инстансе его нет.

Для одного процесса и «своих» это честно написано в комментарии. Если API когда-нибудь окажется за балансировщиком или откроется шире локальной сети, лимит надо переносить в Postgres или Redis до того, как на него начнут опираться. Отдельно: если переменная общего токена не задана, `aiGate` пускает анонима (`if (!user && token && …)`). Для локальной разработки так и задумано. В проде отсутствие токена не должно молча открывать оплачиваемый эндпоинт; лучше отказывать в старте, когда `NODE_ENV=production`, а токена и базы нет.

Проверка `Origin` пропускает изменяющий запрос, у которого заголовка нет. С текущей cookie `SameSite=Lax` чужой сайт такую cookie на POST не приложит, так что дыры нет. Если cookie когда-нибудь станет `SameSite=None`, отсутствие `Origin` надо будет отвергать, а не пропускать. Это стоит одной строкой рядом с `csrfGuard`, чтобы следующий автор не «ослабил SameSite» отдельно от гарда.

### Модель зашита строкой, и это нормально, пока строка существует

`GRADER_MODEL` по умолчанию `claude-haiku-5-5`, переопределяется окружением. Падение модели превращается в 502 `examiner_failed` без тела исключения клиенту — так и нужно. Стоит только не логировать сам ответ кандидата рядом с ошибкой провайдера, если логи когда-нибудь уедут наружу: сейчас `console.error('grade failed', error)` ошибку провайдера пишет, текст ответа — нет. Это уже аккуратно.

## Качество кода

Стиль ровный: маленькие модули, типы на границе, Zod на входе HTTP и на YAML, комментарии объясняют ограничение, а не пересказывают строку. `any` по репозиторию почти нет. Пароли и токены не собраны вручную на строках.

Замечания точечные, не про «переписать всё»:

- Состояние карточки урока продублировано, см. выше. Это главный структурный долг.
- `plural` для русских числительных есть и в `packages/core/src/reminders.ts`, и локально в `apps/web/src/demo/Landing.tsx`. Вторая копия уже разошлась по записи (другая проверка `mod100`). Одному месту в core здесь самое место: строки интерфейса всё равно завязаны на те же правила.
- Каталог вопросов (`apps/web/src/pages`) и демо-путь не делят компоненты упражнений, и это правильно: у каталога другие экраны. Путаница начнётся, если в каталог добавят quiz из банка и напишут третий отрисовщик. Точка расширения уже есть: `quizByQuestion` в `apps/web/src/data/quizzes.ts`.
- Проверка доступа в API и форум покрыты тестами (`app.test.ts`, `accounts.test.ts`, `forum.test.ts`). Клиентские экраны каталога и урока — нет. Для статического контента это терпимо, для двух реализаций одной карточки — уже нет: достаточно одного теста на хук состояния, общего для обеих платформ.

## Что сделать дальше

1. Обновить схему в README до фактического дерева и версий, на которых помечен контент. Иначе следующий автор будет сверяться не с тем релизом.
2. Вынести состояние упражнения (выбор, shuffle, «уже отвечено») в `@rr/core` и оставить в web/mobile только вёрстку. После этого один тест фиксирует поведение обеих платформ.
3. Добавить в проверку контента прогон predict-output и не пускать в банк пример, который соседний find-bug называет ошибкой. Порог длины тела имеет смысл поднять для уровня senior или хотя бы не считать 400 символов ответом на архитектурный вопрос.
4. Перед любой публичной выкладкой API: отказ стартовать без токена или базы в production, и вынос суточной квоты из `Map` процесса. In-memory лимит форума можно оставить, пока инстанс один, но комментарий стоит продублировать в месте, где задаётся `dailyLimit`, а не только над классом.
5. Сборку мобильного бандла контента прицепить к той же команде, которой собирают веб, чтобы `content.json` не жил отдельной памятью.
